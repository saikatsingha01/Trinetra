AI Subsystem V3 — Bug Fix Roadmap
Scope

V3 is a bug-fix phase only.

Do not redesign the V2 architecture. Do not add unrelated features. Do not modify working V2 components unless a change is directly required to fix one of the issues below.

The following issues were identified from the first real manual end-to-end test of the V2 pipeline.

Issue 1 — Attachment Conclusions Are Empty
Problem

The supplied evidence contained:

"malicious": true

for an embedded attachment, and the pipeline extracted:

malicious_attachment
high_abuse_confidence

However, the final AIAssessment returned:

"attachment_risk_detected": false,
"malicious_attachment_detected": false,
"attachment_findings": []
Required Fix

Ensure supported forensic signals are correctly reflected in the attachment-related fields of AIAssessment.

A supplied explicit malicious attachment finding should be capable of producing:

"attachment_risk_detected": true,
"malicious_attachment_detected": true,
"attachment_findings": [...]

Preserve exact evidence provenance.

Do not duplicate the raw forensic tree.

Issue 2 — Unsupported Claims in AI Explanation
Problem

The output claimed:

The actor group 'FIN7' is known for BEC activities

but the supplied evidence only contained:

"actor_groups": ["FIN7"]

The AI must not introduce outside knowledge as if it came from the evidence.

Required Fix

Ensure explanations remain strictly evidence-grounded.

The AI must not invent:

malware names
threat-intelligence results
actor capabilities
actor relationships
campaign relationships
reputation information
external facts
detections not present in the evidence

Do not simply remove explanations. The AI must still provide useful evidence-based reasoning.

Issue 3 — Excessive Processing Time
Problem

The first manual test took approximately:

501 seconds
≈ 8.35 minutes

for a relatively small evidence package.

The system was running:

deepseek-r1:32b

locally through Ollama.

Required Fix

Profile the pipeline and determine where the time is being spent.

Check:

LLM inference time
repeated LLM calls
retries
timeout/wait behavior
unnecessary processing
oversized prompts
loops
grounding time
other pipeline stages

Only make safe optimizations.

Do not replace DeepSeek-R1 32B.

Do not add another model.

Do not use external APIs.

Do not remove required security, validation, or grounding stages merely for speed.

If inference is simply slow because of the hardware/model combination, document that instead of making an unsafe optimization.

Issue 4 — Suspicious File Type Is Being Treated Too Strongly
Problem

A file extension such as:

payload.exe

is only a weak indicator.

A file being an .exe does not by itself prove that it is malicious.

Required Fix

Ensure:

suspicious_file_type

remains a weak observation unless stronger supplied evidence exists.

The AI must distinguish between:

.exe → suspicious file type

and:

malicious: true → explicit malicious detection

Do not allow file extension alone to produce:

malware_detected

or equivalent strong conclusions.

Issue 5 — Abuse Confidence Must Not Become Malware Detection
Problem

The evidence contained:

"abuseConfidenceScore": 100

This can support a high-abuse-confidence signal, but it is not automatically proof that an attachment itself is malware.

Required Fix

Maintain the distinction between:

high_abuse_confidence

and:

malware_detected

An abuse-confidence score must not automatically become a malware detection.

Only explicit supplied malware evidence may support a malware conclusion.

Issue 6 — SHA-256 Must Not Be Treated as Proof of Maliciousness
Problem

A SHA-256 value identifies a file:

"sha256": "..."

but the hash itself does not prove that the file is malicious.

Required Fix

Ensure the AI does not conclude:

malicious file

merely because a SHA-256 exists.

A hash should support a malicious-hash conclusion only when the supplied evidence explicitly associates that hash with malicious/threat-intelligence information.

The original SHA-256 must remain unchanged throughout the pipeline.

Issue 7 — Assessment, Findings, and Grounding Must Agree
Problem

The manual output had a contradiction:

The explanation stated:

The attachment contains a malicious executable

and grounding accepted the underlying evidence, but:

"malicious_attachment_detected": false,
"attachment_findings": []
Required Fix

Ensure the final assessment is internally consistent.

If the AI makes a supported attachment conclusion, the structured attachment fields should represent that conclusion appropriately.

The relationship should be:

Evidence
   ↓
Forensic Signal
   ↓
AI Finding
   ↓
Grounding
   ↓
Final Assessment

Do not allow the explanation, structured findings, and grounding result to contradict one another.

Issue 8 — AI Must Not Use Outside Knowledge
Problem

The AI currently has the potential to turn supplied identifiers into external factual claims.

For example:

"actor_groups": ["FIN7"]

does not mean the evidence supplied:

FIN7 performs BEC

Likewise, a country, ISP, domain, filename, or other contextual attribute must not automatically be interpreted as malicious.

Required Fix

Strengthen the evidence-only behavior.

The AI may interpret supplied evidence, but it must not supplement it with external knowledge.

Especially prevent unsupported conclusions based solely on:

country
ISP
actor name
domain name
file extension
filename
IP address
hash existence
reputation assumptions
contextual associations
Issue 9 — Manual Test Harness Must Remain Disposable
Problem

The manual testing system is only for validating the V2 pipeline before backend integration.

It must not become part of the production AI architecture.

Current structure:

manual_test/
├── input/
│   └── sample_evidence.json
├── output/
│   └── analysis_result.json
└── run_manual_test.py
Required Fix

Ensure the manual harness remains completely disposable.

Requirements:

input/ contains manually supplied test evidence.
output/ contains generated results.
Deleting input/ must not break the AI subsystem.
Deleting output/ must not break the AI subsystem.
Deleting the entire manual_test/ directory must not break the AI subsystem.
The production pipeline must not import anything from manual_test/.
No production module may depend on the manual test files.
The harness must invoke the existing pipeline rather than creating a second pipeline.
Do not move manual-test logic into src/ai/.
